# Phase 5 错题本

> 只收实机真实踩过的。每条：**看到什么 → 为什么 → 怎么修**。（2026-10-08，WSL2/x86_64）

## W3：Exec 验收通道

### 1. curl 没加 `-f`，API 配错了程序还当成功

- **看到什么**：`go run .` 跑完，`InstanceStart` 返回成功，但 ssh 轮询 60 秒超时：`panic: ssh 172.16.0.2 60s 未就绪`。回头查，配网卡那步 API 其实返回了 4xx。
- **为什么**：curl 默认 4xx/5xx 也返回退出码 0。Go 只看了"curl 启动成功"，没看 HTTP 状态。
- **怎么修**：`api()` 里 curl 加 `-f`（后来 W4 换成 `--fail-with-body`，见第 5 条）。**API 调用必须看 HTTP 状态，不能只看进程退出码。**

### 2. boot_args 漏了 `ip=`，客户机 eth0 没有地址

- **看到什么**：同上，`ssh 172.16.0.2 60s 未就绪`；`ip neigh show dev tap0` 显示 `172.16.0.2 FAILED`——宿主发了 ARP，客户机零回应。
- **为什么**：客户机 IP 不是 DHCP 来的，是内核启动参数配的。我们的 `boot_args` 只有 `console=ttyS0 reboot=k panic=1 pci=off`，漏了 `ip=172.16.0.2::172.16.0.1:255.255.255.252::eth0:off`（3-5 README 第 228 行有原文）。
- **怎么修**：补上 `ip=` 参数。
- **教训**：由这条挖出 W2 的"跑通"是**假阳性**——当时 ssh 连上的很可能是 3-5 残留的老 VM（它的 boot_args 是对的），不是我们新起的。重启清掉残留后真相暴露。**验收必须连到"这次"起的实例。**

## W4：快照/回放

### 3. 快照前没暂停 VM，直接拍被 400 拒绝

- **看到什么**：`panic: API PUT /snapshot/create 失败: exit status 22`（body 还是空的，当时看不到原因）。
- **为什么**：Firecracker 要求 VM 先暂停。手动裸调 curl 才看到真正原因：`{"fault_message":"Create snapshot error: Cannot save the microVM state: Operation not allowed: save/restore unavailable while running"}`。
- **怎么修**：`Snapshot()` 里先 `PATCH /vm` `{"state":"Paused"}`，再调 `snapshot/create`。

### 4. `snapshot/load` 不认 `snapshot_type` 字段

- **看到什么**：`panic: API PUT /snapshot/load 失败`，这次 body 看到了：`unknown field 'snapshot_type', expected one of 'snapshot_path', 'mem_file_path', ... 'resume_vm' ...`。
- **为什么**：`snapshot/create` 和 `snapshot/load` 是两个 endpoint，字段不对称。create 要 `snapshot_type`（Full/Diff），load 不要——类型信息在快照文件里，加载时自己读。
- **怎么修**：load 的 body 去掉 `snapshot_type`，只留 `snapshot_path`/`mem_file_path`/`resume_vm`。
- **教训**：别脑补 API 是对称的，报错信息列的期望字段就是文档。

### 5. curl 的 `-f` 会吞掉错误 body，排错时失明

- **看到什么**：第 3 条的 panic 信息里 body 是空的，只能看到 `exit status 22`，被迫手动裸调 curl 才看到 `fault_message`。
- **为什么**：`-f` 在 HTTP 报错时直接丢弃 body。想要"报错退出码非零"又想要"body 留着"，要用 `--fail-with-body`（curl 7.76+）。
- **怎么修**：`api()` 里 `-f` 换成 `--fail-with-body`。换完第 4 条的报错一次就定位了，不用裸调。

### 6. firecracker 的 Exec 必须给参数加 shell 引号，runc 的不能加

- **看到什么**：两次"快照失败"都是冤案。① `sh -c "nohup sleep 300 ... & echo $!"` 传过去，远端实际执行的是 `sh -c nohup`（`-c` 只吃紧跟的下一个参数），后台起的是个空 nohup；② `pgrep -f "sleep 300"` 报 `exit status 2`（pgrep 语法错误：只接受一个 pattern，空格把它拆成了两个）。
- **为什么**：ssh 会把参数用空格拼成一行，远端 sshd 套 `sh -c` 再解析一次——**必经 shell**；`docker exec` 是直接 exec，**不经过 shell**。同一个 `Exec` 接口，两种传输语义。
- **怎么修**：`FirecrackerRuntime.Exec` 里每个参数加单引号（`'...'`，内嵌单引号转义）；runc 那边不加——加了反而往参数里掺脏东西。
- **教训**：排错时先怀疑测试本身，再怀疑被测对象。经 ssh 传复合 shell 命令时，你写的和远端实际解析的可能是两回事。

### 7. `pkill -f` 会杀掉自己的 shell

- **看到什么**：`ssh PCGaming "pkill -f firecracker-v1.17; ..."` 直接 `exit 255`，ssh 断了。
- **为什么**：`-f` 匹配完整命令行，而执行 pkill 的那个 shell 自己的命令行里就带着 `firecracker-v1.17`——自己把自己杀了。
- **怎么修**：用 `pkill -f '[f]irecracker-v1.17'`，方括号让 pattern 匹配进程名但匹配不上字面命令行。
