# Phase 4 学习笔记

> K8s 编排与调度（KTHW 精简版）。Session 4-1 ~ 4-4 完成于 2026-10-07，
> 4-5（CNI）进行中，WSL2 k3s 单节点实机。

## 一句话

K8s 没有魔法：apiserver 是账本唯一的出入口，scheduler 只分房，
controller-manager 只数数，kubelet 只认领写着自己名字的 pod——
所有组件都是 watch 账本干活。

## 关键链条（背下来）

```
kubectl → apiserver（认证→授权→写 etcd/kine）
  → deployment 控制器建 replicaset（期望副本数）
  → replicaset 控制器建 pod（nodeName 为空）
  → scheduler 过滤→打分→bind，写回 nodeName
  → 该节点 kubelet（fieldSelector watch）认领
  → CRI → containerd → runc 起容器 → CNI 分 IP → 状态写回 Running
```

## 六个"啊哈"时刻

1. **证书即身份**：`client-admin.crt` 的 `subject=O=system:masters`
   就是 cluster-admin 权限的来源——权限写在证书里，不在 kubectl 里。
   apiserver 两步走：验签名认发证机关（认证）→ 看 subject 的组给 RBAC（授权）。
   kubeconfig 的 users 块 base64 解码出来，就是这张证书。
2. **etcd 是笨 KV**：所有 K8s 语义（认证鉴权/对象校验/多版本转换/watch）
   全部收敛在 apiserver。k3s 把 etcd 换成 sqlite（kine 伪装成 KV 接口），
   scheduler 和 kubelet 一行代码不用改——这就是"唯一出入口"的价值：存储层可替换。
3. **requests 是给 scheduler 看的**：hungry pod（`requests.memory=100Gi`）
   → `FailedScheduling: 0/1 nodes are available: 1 Insufficient memory`。
   requests 管调度（scheduler 过滤用），limits 管执行（kubelet 转成 cgroup 上限）。
4. **kubelet 是 pull 不是 push**：apiserver 从不"派活"。kubelet 启动时用
   `fieldSelector=spec.nodeName=<自己节点名>` watch，只认领写着自己名字的 pod。
   没被 bind 的 pod，它连看都看不到。
5. **deployment 不建 pod**：deployment → replicaset → pod 三级链，
   pod 名 `demo-d8bcf9bfd-xxx` 的三段结构就是证据。
   `scale` 改期望 → 调谐循环补 pod；`delete deployment` → 级联删除，一个不留。
6. **k3s 的 CNI 配置不在标准路径**（4-5 实机踩的坑）：`ls /etc/cni/net.d/`
   报 `ls: cannot access '/etc/cni/net.d/': No such file or directory`——
   sudo 也一样，说明不是权限问题，是这目录真的不存在。
   k3s 把 CNI 收拢在 `/var/lib/rancher/k3s/agent/etc/cni/net.d/10-flannel.conflist`。
   `name=cbr0`，插件链 flannel（管跨节点路由，delegate 里的
   hairpinMode/forceAddress/isDefaultGateway 是透传给 bridge 插件的参数，
   bridge + host-local(IPAM) 都藏在这一层）+ portmap + bandwidth。

## 实证命令（都亲手跑过）

- 证书四组：`sudo ls /var/lib/rancher/k3s/server/tls/`（client-ca/server-ca、
  client-* 身份证、serving-* 门牌、etcd/service/request-header）；
  `openssl x509 -subject -issuer` 看持证人/发证机关；
  `openssl verify -CAfile client-ca.crt client-admin.crt` → OK。
- 账本：`sudo ls /var/lib/rancher/k3s/server/db/` → `state.db`（sqlite 模式）；
  python3 读 kine 表，key 格式 `/registry/<API分组>/<资源>/<名>`；
  `kubectl create configmap demo-42` → 账本里抓到
  `/registry/configmaps/default/demo-42` → 验证完删除。
- 调度：hungry pod `kubectl describe` → Events 里 default-scheduler 的
  FailedScheduling；ok pod `kubectl get -o wide` →
  `NODE=pcgaming / IP=10.42.0.19 / Running`，一行串起 bind + CNI + kubelet。
- 调谐：`kubectl create deployment demo --replicas=3` →
  `kubectl get replicaset` 3/3/3 → `scale --replicas=5` → 5 个 Running →
  `delete deployment` → 5 个 pod 全 Terminating。
- CNI（4-5，k3s）：`ls /etc/cni/net.d/` → `No such file or directory`
  （标准路径在 k3s 不存在）；
  `sudo cat /var/lib/rancher/k3s/agent/etc/cni/net.d/10-flannel.conflist`
  → `name=cbr0`，插件链 flannel + portmap + bandwidth。

## Session 4-5 回顾：CNI（2026-10-07）

- k3s 的 CNI 配置不在标准路径 `/etc/cni/net.d`，而在
  `/var/lib/rancher/k3s/agent/etc/cni/net.d/`（`10-flannel.conflist`）。
- 插件链：`flannel`（跨节点路由，`delegate` 里透传参数给 bridge；
  bridge 建网桥、host-local 即 IPAM 分 IP，都藏在这一层）
  + `portmap`（端口映射）+ `bandwidth`（限速）。
- 插件是可执行文件：`/var/lib/rancher/k3s/data/*/bin/`（bridge/flannel/
  host-local/portmap/loopback…，跟 JSON 的 type 对得上）。
- 网桥实际叫 `cni0`（UP 的那块，不是 conflist 里 `name` 的 cbr0；
  virbr0/docker0 都 DOWN，无关），IP `10.42.0.1/24`，pod 从 .2 起分。
- 谁调：kubelet → CRI → containerd 按 JSON 链调插件；
  什么时候：sandbox 创建时 ADD，pod 删除时 DEL（先有网再有 Running）；
  IPAM（host-local）：只分 IP 不管网卡。

## Session 4-6 回顾：RuntimeClass（2026-10-07）

- RuntimeClass = "runtime 菜单"：pod 写 `runtimeClassName: gvisor`，
  kubelet 查表用 runsc 起 sandbox；不写用默认 runc。
- pod sandbox 是"坑位"，runc/gVisor/Kata 是"填坑的材料"——
  multi-runtime 的本质就是按任务选隔离强度，统一编排。
- 后厨真相：containerd 只认 `config.toml` 里的 `runtimes.*`；
  kata 的 drop-in（`config-v3.toml.d/kata-deploy.toml`）没被这版 k3s
  吃进去（`grep -c kata config.toml` = 0），菜单还在、厨子不认。
- 亲手加菜：`config.toml` 存成 `config.toml.tmpl` 模板并追加 runsc 段
  （`runtime_type = "io.containerd.runsc.v1"`）→ `systemctl restart k3s`
  → 验证 config.toml 吃进 → 建 RuntimeClass `gvisor`（handler: runsc）。
- 验收：`gvisor-demo` 内 `uname -r` = `4.19.0-gvisor`，
  `runc-demo` = 宿主内核 `6.18.40.1-microsoft-standard-WSL2`——
  同一集群、两种 sandbox，同框。
- 接入新 runtime 的两处：① 后厨 `config.toml.tmpl` 加 runtime
  （模板持久化，直接改 config.toml 会被 k3s 重启重写）；
  ② 建 RuntimeClass 对象（handler 对上后厨名）。

## 附：相关问答

- **daemon 是什么**：一直在后台跑、等着干活的服务进程。你敲的 `docker run`
  只是客户端，真正干活的是 dockerd；sshd、containerd 同理。
  daemon 三特征：一直在、藏在后台、别人经 socket/API 使唤它。
- **"gVisor 启动开销被 Docker 固定开销掩盖"**：一次 `docker run` ≈
  Docker 固定开销（约 400ms，自带几十 ms 抖动）+ runtime 自身启动
  （runc 几 ms，runsc 几十 ms）。451 vs 466 的 15ms 差距掉进噪声里，
  说明不了问题；3-3 去掉 Docker 裸测才看到 4.5x。
- **3-5 为什么走 docker**：WSL 的 containerd socket 与 `ctr` 默认的不一致，
  `ctr plugins ls` 看不到 runsc；`docker --runtime=runc|runsc`
  是当时唯一两组都跑通的 harness（代价就是上面的掩盖，见
  phase-3-sandbox-compare/impl/README.md）。
- **kubeconfig 三块**：clusters（apiserver 地址 + 集群 CA）、
  users（client 证书/key 或 token，base64 内嵌只是编码不是加密）、
  contexts（两者绑定）。多集群 = 往数组里 append +
  `kubectl config use-context` 切换；把 `server: 127.0.0.1:6443`
  改成服务器对外 IP，别的机器就能远管这个集群。
