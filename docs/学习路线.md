## 二、ADHD 学习协议（请先读这 6 条）

1. **一个 session 只干一件事**：下面每个 session 都是「一句话目标 + 一组命令 + 一个验收动作」。
2. **25–40 分钟硬停**：到点没做完就停，下个 session 继续。 unfinished ≠ 失败。
3. **先动手，后看文档**：每个 session 先跑命令，遇到不懂的再回头查，不预习。
4. **打卡**：做完在 session 后面打 ✅，中断了打 ⏸️ 并写一句卡在哪。
5. **不囤教程**：材料只看路线里列的那一个，看完就关。
6. **每周节奏**：3–4 个 session，留 1 个 session 做阶段项目。某天状态差就只做 15 分钟的「最小 session」（每个阶段都标注了）。

## 三、环境准备（一次性，约 30 分钟）

本项目兼容 Apple Silicon Mac（M3/M4）。Phase 3 的 KVM/Firecracker 可在本地 Linux VM 中运行，无需云主机。

- **Linux 实验机**：在 Mac 上用 Lima 起一台 ARM64 Linux VM（Apple Virtualization 后端）。所有需要 root / cgroup / netns / runc / KVM 的实验都在 VM 里做；纯 Go 的部分（如手写 OCI 镜像工具）可直接在 Mac 上跑。
  ```bash
  brew install lima
  limactl start --name=sandbox template://ubuntu --nested-virt
  # 进 VM 验证：ls /dev/kvm 存在即成功
  ```
  - 关键配置：`vmType: vz` + `nestedVirtualization: true`（Apple 只在 M3+ 开放嵌套虚拟化）。
  - 若 `/dev/kvm` 没出现：优先用 Ubuntu 24.04 镜像（有项目报告 6.19+ 内核在 ARM 嵌套虚拟化上有回归，不确定是否已修复）。
- **不建议用 Docker Desktop 做实验机**：其内置 Linux VM 不便直接操作 runc、cgroup。
- **Phase 3 说明**：Firecracker 有 aarch64 版本，在 ARM64 Linux + `/dev/kvm` 下可直接跑；gVisor/Kata 也有 ARM 支持。
- 通用：Linux VM 里装 Docker、Go 1.22+、git、curl；Mac 本机装 Lima。

## 六、Phase 2：Linux 隔离与安全原语（2–3 周）

**目标**：把 namespace 之外的隔离手段补齐。「资源隔离、网络隔离」的核心就是这一阶段。

### Session 2-1｜cgroups v2 动手（30 分钟）
- 一句话目标：亲手建 cgroup、设内存上限、看 OOM killer 干活。
- 动手（跟着敲，不用预习）：
  ```bash
  sudo mkdir /sys/fs/cgroup/demo
  echo "100M" | sudo tee /sys/fs/cgroup/demo/memory.max
  echo $$ | sudo tee /sys/fs/cgroup/demo/cgroup.procs
  cat > /tmp/membomb.go <<'EOF'
  package main
  import ("fmt"; "os"; "os/signal"; "syscall")
  func main() {
      b := make([]byte, 200<<20); for i := range b { b[i] = 1 }
      fmt.Println("200M 已占满，赖着不走")
      ch := make(chan os.Signal, 1); signal.Notify(ch, syscall.SIGTERM, syscall.SIGINT); <-ch
  }
  EOF
  # 别用 select{} 常驻——Go deadlock 检测会 panic（见 Phase 1 Session 1-2 常见坑）
  go build -o /tmp/membomb /tmp/membomb.go
  # 完整可复制步骤见 phase-2-container-v2/README.md Session 2-1
  ```
- 材料：[HPC 课程的 cgroups v2 实操（§2.6）](https://github.com/foundations-of-hpc/high-performance-computing-at_units/blob/HEAD/Cloud/Notes/Lecture_04_Notes_Containers.md) ——只看 §2.6 一节。
- 验收：说出 `memory.max`、`cpu.max`、`cgroup.procs` 三个文件的作用。

### Session 2-2｜给自制容器加上 cgroup 限制（35 分钟）
- 一句话目标：把 Phase 0 的 container-from-scratch 接上 cgroup v2。
- 动手：容器进程启动后，把它的 PID 写进你建的 cgroup；或者在 Go 里用 `os.MkdirAll` + `os.WriteFile` 直接写文件。
- 验收：容器里跑内存炸弹，宿主机不受影响。

### Session 2-3｜seccomp + capabilities（35 分钟）
- 一句话目标：知道怎么限制容器能用的系统调用。
- 动手：
  1. `docker run --security-opt seccomp=unconfined` 对比默认，跑 `unshare` 看区别（感受 profile 的存在）。
  2. 在自制容器里，用 Go 的 `unix.Prctl`（`golang.org/x/sys/unix`）或 runc 的 `config.json` 加 `linux.seccomp` 段，禁掉几个危险调用。
- 材料：runc 默认 seccomp profile 源码（`/etc/docker/seccomp` 或 runc 仓库里找 `seccomp.json`，只看结构）。
- 最小 session：只做第 1 步，知道 seccomp 是什么就行。

### Session 2-4｜overlayfs（30 分钟）
- 一句话目标：亲手 mount 一个 overlay，理解镜像分层。
- 动手：
  ```bash
  mkdir -p lower upper work merged
  echo hello > lower/file
  sudo mount -t overlay overlay -o lowerdir=lower,upperdir=upper,workdir=work merged
  ```
  改 `merged/file`，观察 upper/lower 的变化。
- 验收：说出镜像的「层」和 overlay 的 lowerdir 是什么关系。

### Session 2-5｜容器网络：netns + veth + NAT（40 分钟）
- 一句话目标：亲手给两个 netns 连上网。
- 动手：
  ```bash
  sudo ip netns add ns1
  sudo ip link add veth-host type veth peer name veth-ns1
  sudo ip link set veth-ns1 netns ns1
  # 配 IP、起网卡、加 NAT（iptables MASQUERADE）
  sudo ip netns exec ns1 ping 8.8.8.8
  ```
- 验收：`ns1` 能 ping 通外网，且宿主机 `ip addr` 看不到 ns1 的 IP（隔离感）。
- 卡住降级：先只做到两个 netns 互 ping，NAT 下个 session 做。

### 📦 Phase 2 项目：自制容器 v2.0（Go，2–3 个 session）
在 Phase 0 代码基础上加（建议用 Go 重写或封装）：
1. cgroup v2 资源限制（CPU/内存）。
2. seccomp profile（默认禁 mount/reboot 等）。
3. 网络（veth + NAT，或复用 Session 2-5 的脚本）。
- 代码放在 `phase-2-container-v2/impl/`，测试用例见 `phase-2-container-v2/tests/TESTS.md`。
- 验收：v2.0 跑起来，一个 `README.md` 写清楚加了哪三层隔离、每一层防什么。

### Phase 2 出口验收
1. 手建 cgroup 限内存并触发 OOM。
2. 手配 netns + veth + NAT 让隔离网络能上网。
3. 自制容器 v2.0 跑通 + README。

## 七、Phase 3：虚拟化与轻量沙盒（3–4 周）

**目标**：虚拟化与轻量沙盒——KVM/QEMU、轻量虚拟机、快照、资源隔离。这是和纯容器差异最大的一部分，建议放慢节奏。

### Session 3-1｜KVM 上手：起一台 VM（40 分钟）
- 一句话目标：用 cloud image 起一台 **ARM64** Ubuntu VM，打快照再恢复。
- 完整讲义（含复制粘贴命令）：`phase-3-sandbox-compare/README.md` 的 Session 3-1。
- 关键：VM 是 ARM64，镜像必须用 arm64（`jammy-server-cloudimg-arm64.img`），不要用 amd64 installer。
- 材料：[KVM/QEMU 命令行完整教程](https://github.com/solo2121/sysadmin-security-lab/blob/HEAD/docs/guides/infrastructure/managing-kvm-qemu-cli-tutorial.md) ——当命令手册查，不通读。
- 验收：`virsh list` 看到 VM，`virsh snapshot-create-as` 打一个快照再恢复。

### Session 3-2｜Firecracker：启动第一个 microVM（40 分钟）
- 一句话目标：跑通官方 getting-started，ssh 进 microVM。
- 完整讲义：`phase-3-sandbox-compare/README.md` 的 Session 3-2（注意下 aarch64 的二进制和 kernel）。
- 动手：跟着 [Firecracker 官方 getting-started](https://github.com/firecracker-microvm/firecracker/blob/HEAD/docs/getting-started.md) 一步步敲（下载 kernel + rootfs → 配 tap 网络 → curl 调 API → ssh）。
- 验收：进 microVM 跑 `uname -r`，确认和宿主机内核版本不一样。
- 卡住降级：网络那节先跳过，只要能进 serial console 就算过。

### Session 3-3｜gVisor：换个 runtime 跑容器（30 分钟）
- 一句话目标：用 `runsc` 跑容器，感受「用户态内核」。
- 完整讲义：`phase-3-sandbox-compare/README.md` 的 Session 3-3。
- 动手：跟着 [gVisor containerd 快速上手](https://github.com/google/gvisor/blob/HEAD/g3doc/user_guide/containerd/quick_start.md) 安装 runsc，用 `ctr run --runtime io.containerd.runsc.v1` 跑 busybox，进容器跑 `dmesg` 看 gVisor 的启动日志。
- 验收：说出 gVisor 和 runc 隔离边界的区别（一句话）。

### Session 3-4｜Kata Containers：K8s 里的轻量 VM（35 分钟）
- 一句话目标：在 K8s 里用 RuntimeClass 跑起 Kata pod。
- 完整讲义：`phase-3-sandbox-compare/README.md` 的 Session 3-4（k3s 单节点；本节可暂缓，不阻塞 3-5）。
- 动手：跟着 [Kata 官方 quick-start](https://github.com/kata-containers/kata-containers/blob/HEAD/docs/quick-start-guide.md)（helm 装 kata-deploy → apply 一个 `runtimeClassName: kata` 的 pod → `kubectl logs` 看 guest 内核版本）。
- 前置：需要一个能跑 K8s 的环境（k3s/kind 都行，Phase 4 会细讲；这里先用最省事的 k3s 单节点）。
- 验收：pod 的 `uname -r` 是 guest 内核。

### Session 3-5｜自研：三方案对比评测（40 分钟，步骤已预置）
- 一句话目标：输出一张对比表，这是面试时能讲 10 分钟的东西。
- 完整讲义：`phase-3-sandbox-compare/README.md` 的 Session 3-5（含 bench.go 完整代码）。
- 动手（Go 程序 `bench.go`）：
  1. 测启动耗时：runc / runsc / firecracker 各起 5 次，取中位数。
  2. 测内存开销：启动后看宿主机新增内存。
  3. 填表：隔离边界（进程级 / syscall 拦截 / 硬件虚拟化）、启动速度、内存开销、适用场景。
- 验收：一张 markdown 表格 + 3 条结论（比如「Agent 沙盒选谁」）。

### 📦 Phase 3 项目：sandbox-compare（2 个 session）
把 Session 3-5 的程序整理成仓库：`bench.go`（放在 `phase-3-sandbox-compare/impl/`）+ `RESULTS.md`（对比表+结论）+ 环境说明。测试用例见 `phase-3-sandbox-compare/tests/TESTS.md`。

## 九、Phase 5：沙盒平台 Capstone（4–6 周）⭐

**目标**：把前面全部串起来，做一个覆盖岗位 5 大能力的作品。这是简历上最有分量的一项。

### 项目：mini-sandbox（Go）
一个 Go 写的沙盒任务平台（单机版，不用分布式）：

| 岗位能力 | 对应模块 | 做法 |
|---|---|---|
| 1. 大规模沙盒平台、稳定可扩展的虚拟化环境 | 并发任务池 | goroutine worker pool 跑 N 个沙盒任务，记录成功率/耗时 |
| 2. VM/容器统一接入、编排调度、可复用抽象 | `Runtime` 抽象类 | `ContainerRuntime(runc)` + `MicroVMRuntime(firecracker)` 实现同一接口：`create/start/stop/destroy` |
| 3. 多任务环境适配、统一 runtime、验收标准 | 环境模板 | YAML 定义环境（镜像/kvm 配置/验收脚本），`verify` 命令跑验收 |
| 4. 网络代理、隔离、连通性治理 | 网络模块 | 每个沙盒独立 netns；全局 egress 代理（tinyproxy 或自写转发）；连通性自检 |
| 5. 生命周期管理：创建/镜像/调度/恢复/快照/回放 | 生命周期 + 快照回放 | `snapshot/restore`（容器用 overlay upper 层打包，VM 用 virsh 快照）；操作日志 JSONL，`replay` 命令可复现回放 |

### 里程碑（每周 1 个）
- W1：`Runtime` 抽象 + runc 后端跑通。
- W2：firecracker 后端跑通（复用 Phase 3）。
- W3：镜像管理（复用 Phase 1 的 mini-oci）+ 环境模板 YAML。
- W4：快照/恢复 + 操作日志回放。
- W5：网络隔离 + egress 代理 + 连通性自检。
- W6：并发压测 + README + demo 录屏。

### 验收
1. `go run ./impl run --runtime firecracker --template demo-task` 一条命令起任务。
2. 任务失败后 `replay` 能复现。
3. README 写清架构图（手画拍照也行）+ 5 大能力映射表。
4. （可选）录制 3 分钟 demo，用于复盘讲解。
- 代码放在 `phase-5-mini-sandbox/impl/`，测试用例见 `phase-5-mini-sandbox/tests/TESTS.md`。

## 十一、节奏换算 & 降级清单

**节奏换算**（总时长按 session 数 ≈ 45 个 session 估算）：
- 每周 4 小时（2 session）：约 22 周
- 每周 8 小时（4 session）：约 12 周
- 每天 1 session：约 9 周

**卡住时的降级清单**（按顺序试）：
1. 把 session 拆成两半，只做前一半。
2. 先抄命令跑通，再回头理解（允许「先会用」）。
3. 跳过该 session，继续下一个（路线是网状的，不是单链）。
4. 卡超过 2 个 session：寻求外部帮助（结对、社区提问），把这一步拆成「填空式」任务。
5. 某一整阶段学不动：先做下一阶段的入口自测，能过的阶段先拿下。
