# Phase 3 错题本

> 只收实机真实踩过的。每条：**看到什么 → 为什么 → 怎么修**。来源：3-1、3-2、3-3 实机记录（2026-10-06，WSL2/x86_64）。

## 1. Apple Silicon 的嵌套虚拟化起不了 guest（`/dev/kvm` 存在也没用）

- **看到什么**：三连击，一层比一层深。
  1. `virt-install` 起 ARM64 云镜像 → **固件层** `Synchronous Exception at 0x00000000B805FB2C`，连内核都没进。（libvirt 自动选的是 `AAVMF_CODE.secboot.fd`，加载 `shimaa64.efi` 时崩。）
  2. 换非 secboot 固件（`-bios /usr/share/AAVMF/AAVMF_CODE.fd`）→ 内核起来了、认出磁盘（`vda1/vda15`）和 seed 盘（`vdb`），但 **guest 时钟跑得比墙钟快 2.3 倍**：内核报 `rcu: INFO: rcu_sched detected stalls` 时写着 `t=15002 jiffies`，而墙钟只过了 **64 秒**。
  3. 时钟不可信 → initramfs 里的 udev 等不到事件 → 卡死 → 每次都在 60 秒后 RCU stall。试过 `-smp 1` + GICv2、试过 TCG 纯软件模拟（6 分钟还停在固件画面）——都不行。
- **为什么**：嵌套虚拟化的"转发层"质量不同。**Apple 的 VZ 只做到"KVM 接口能开"，vtimer/中断的嵌套转发不可靠**。而 guest 的一切调度、超时、服务启动都建立在时钟上，时钟一歪，整套就停摆。
  → 所以 `ls /dev/kvm` 通过 **只是必要条件，不是充分条件**。
- **怎么修**：换一台真正能嵌套虚拟化的机器。实测对照（同一份 Ubuntu 云镜像、同一套参数）：

  | 判据 | Mac（Lima / Apple VZ） | WSL2（Hyper-V） |
  |---|---|---|
  | 到 `login:` | ❌ 永远没到 | ✅ **18 秒** |
  | `rcu.*stall` | ❌ 60 秒后必然出现 | ✅ **0 次** |
  | guest 时钟 | ❌ 快 2.3 倍 | ✅ `[13.27s]` / 18 秒墙钟 |
  | guest 内核 ≠ 宿主 | — | ✅ `5.15.0-198-generic` vs `6.18.40.1-microsoft-standard-WSL2` |
  | guest 网络 | — | ✅ cloud-init 认出 `enp0s2` |

- **教训**：**验证环境要看"能不能跑通那件事"，不能只看"设备文件在不在"。** 这跟 Phase 2 学到的是同一类思维：cgroup 的"申请 ≠ 占用"、这里的"接口在 ≠ 能用"——**都要拿实物证据说话**。

## 2. 讲义里几处"照抄会踩"的地方（3-1 实机修正）

- **`demo` / `demo123` 登录不成立**：Ubuntu 云镜像的默认用户是 **`ubuntu`**。实机证据：guest 启动日志里 `ci-info: no authorized SSH keys fingerprints found for user ubuntu.`。seed 里的 `password: demo123` 设的就是 `ubuntu` 的密码。
- **ARM64 云镜像必须走 UEFI**：少了 `--boot uefi` 会停在 `no bootable device`（x86 走 BIOS，不需要）。
- **`genisoimage` 的 `-joliet -rock` 不是可选项**：不加时 iso9660 只保留 8.3 大写短名（`USER_DAT.;1`），cloud-init 找不到 `user-data` 就不认这张盘。iso 卷标必须是 **`cidata`**。

（以上三条已在 `README.md` 的 Session 3-1/3-2 里修正。）

## 3. 复用了"跑过一次"的云镜像 → guest 拿不到 DHCP，卡在 wait-online 无限等

- **看到什么**：`virt-install` 起的 VM 卡在 `A start job is running for Wait for Network to be Configured (1min 12s / no limit)` —— **`no limit` 意味着它不会自己超时**。
- **诊断过程**（宿主侧，很有价值）：libvirt 的 `dnsmasq` 在跑 ✓、`virbr0` = `192.168.122.1/24` ✓，但 `ip neigh show dev virbr0` **空的**、桥接表里没有 guest 的 MAC → **guest 一张 DHCP 请求都没发过**。所以问题在 guest 内部，不在宿主网络。
- **为什么**：我把之前**已经被裸 QEMU 启动过**的 `/tmp/demo-amd64.img` 直接 `cp` 给 libvirt 用了。cloud-init 第一次启动会把网卡配置**固化**进 `/etc/netplan/50-cloud-init.yaml`（那次网卡名是 `enp0s2`）；libvirt 的网卡名不同 → netplan 不认识新网卡 → 网卡不配 IP → 永远等不到"网络已配置"。
- **怎么修**：**别拿"跑过一次"的镜像当母盘**。正确做法是"母盘 + qcow2 派生盘"（磁盘版的分层）：
  ```bash
  sudo wget -c -O /var/lib/libvirt/images/jammy-master.qcow2 https://cloud-images.ubuntu.com/jammy/current/jammy-server-cloudimg-amd64.img
  sudo qemu-img create -f qcow2 -b /var/lib/libvirt/images/jammy-master.qcow2 -F qcow2 /var/lib/libvirt/images/demo.qcow2
  ```
  （临时救活也可以在 guest 里补一条 `match: {name: "en*"}` 的 netplan。）
- **教训**：**"母盘 + 派生盘"是分层思想第三次出现**（Phase 1 镜像 layer → Phase 2 overlay lower/upper → Phase 3 qcow2 backing file）。**实验用的基底一旦被写过，就不再是基底。**

## 4. 快照名在同 domain 下唯一；`snapshot-revert` 后可能直接就是 running

- **看到什么**：① `virsh snapshot-create-as demo snap1` → `domain moment snap1 already exists`；② `virsh start demo` → `Domain is already active`。
- **为什么**：① 上一次尝试已经创建过 `snap1`，名字在同 domain 下唯一（换个名字如 `snap2` 即可，不必删）。② libvirt 快照列表里的 **`State: running`** 表示**内存状态也被存了**；`snapshot-revert` 恢复磁盘时会连内存一起恢复 → domain 直接回到 running，这时**不该**再 `start`。
- **怎么修**：先在宿主 `virsh list` 看状态再决定要不要 `start`：
  | `virsh list` 显示 | 做什么 |
  |---|---|
  | `running` | 直接 `virsh console demo` |
  | 空 / `shut off` | `virsh start demo` |
- **教训**：`already active` 有两种来源（本来就开着 / 快照恢复了内存），**先看状态再动手**。

## 5. `Permission denied` 不等于"文件不存在"

- **看到什么**：guest 里 `ls /root/before-snap` → `Permission denied`，而 `ls /tmp/after-snap` → `No such file or directory`。
- **为什么**：`/root` 是 `0700 root:root`，登录用户 `ubuntu`（uid 1000）列不了它。云镜像**故意禁用 root 登录**但给了免密 sudo。
- **怎么修**：`sudo ls -l /root/before-snap`。
- **教训**：**两种"看不到"要分清**——`Permission denied` 是权限问题，`No such file` 才是"不在"。验证"磁盘回退了没有"时，混淆这两者就会得出错误结论。
- **顺带一条更硬的证据**：回退后 `Last login` 显示的时间**比刚才那次登录更早**——因为 `/var/log/wtmp` 也一起回退了。`/tmp` 文件消失可能被"重启清空"解释，**而日志时间戳变旧只可能因为磁盘状态真的倒退了**。

## 6. `curl ... && echo OK` 判不了 Firecracker API 成功与否

- **看到什么**：配错 kernel 路径的那条 boot-source 命令，明明回了 `{"fault_message":"Boot source error: The kernel file cannot be opened: No such file or directory (os error 2)"}`，后面的 `&& echo "1 boot-source OK"` **照样打印了**。
- **为什么**：`curl` 只要连上 unix socket、拿到 HTTP 响应就返回 0，**不管状态码是 204 还是 400**。`&&` 只看进程退出码，所以 API 报错了 echo 也照打。
- **怎么修**：Firecracker 的 PUT 成功时返回 **204 No Content** → `curl -s` 的输出是**空的**。判据改成：**空输出 = 成功；出现 `fault_message` = 失败**。别再拼 `&& echo OK`。
- **教训**：凡是"调 API"的步骤，**成功判据必须来自响应内容，不是进程退出码**。这条以后调 Kata/k8s API 同样适用。

## 7. v1.17 的 `PUT /drives/{drive_id}`：body 里必须带 `drive_id`

- **看到什么**：`--data '{"path_on_host": "/home/kms/fc/ubuntu-24.04.ext4", "is_root_device": true, "is_read_only": false}'` 打到 `http://localhost/drives/rootfs` → `{"fault_message":"An error occurred when deserializing the json body of a request: missing field \`drive_id\` at line 1 column 97."}`
- **为什么**：v1.17 的 `Drive` 结构体把 `drive_id` 标成必填，**URL 路径里的 `rootfs` 不会自动填进 body**，反序列化缺字段直接 400。
- **怎么修**：body 里加上 `"drive_id": "rootfs"`（和 URL 里的 id 保持一致）：
  ```bash
  sudo curl -s -X PUT --unix-socket /tmp/firecracker.socket \
    --data '{"drive_id": "rootfs", "path_on_host": "/home/kms/fc/ubuntu-24.04.ext4", "is_root_device": true, "is_read_only": false}' \
    http://localhost/drives/rootfs
  ```
  （空输出 = 成功。）
- **教训**：**字段照文档抄，不要凭旧版本记忆删**。`network-interfaces` 的 `iface_id` 同理——那条我们本来就带了，所以一次过。

## 8. kernel 文件名别脑补：实测就是 `vmlinux`

- **看到什么**：`--data '{"kernel_image_path": "/home/kms/fc/vmlinux-6.18.51", ...}'` → `{"fault_message":"Boot source error: The kernel file cannot be opened: No such file or directory (os error 2)"}`。
- **为什么**：`ls ~/fc/` 显示 kernel 文件名就是 `vmlinux`（27882928 字节），没有版本号后缀。是把"内核版本号 6.18.51"脑补成了文件名。
- **怎么修**：先 `ls` 看真实文件名再写路径：
  ```bash
  ls -l ~/fc/ | grep -iE 'vmlinux|vmlinuz|ext4'
  ```
- **教训**：**路径这种东西不许背，`ls` 看一眼只要 2 秒**。版本号 ≠ 文件名。

## 9. gVisor `release/latest` 不再单独发 `runsc` 二进制

- **看到什么**：`curl -fsSL https://storage.googleapis.com/gvisor/releases/release/latest/x86_64/runsc -o runsc` → `curl: (22) The requested URL returned error: 404`；`runsc.sha512` 同样 404。
- **为什么**：官方现在 `latest` 只发布 `gvisor.tar.bz2`（+ 它的 sha512），不再单独发布 `runsc` / `runsc.sha512`。很多第三方教程还写着单独下载，已过时。
- **怎么修**：改走 tarball（官方文档的另一条路）：
  ```bash
  curl -fsSL https://storage.googleapis.com/gvisor/releases/release/latest/x86_64/gvisor.tar.bz2 -o gvisor.tar.bz2
  curl -fsSL https://storage.googleapis.com/gvisor/releases/release/latest/x86_64/gvisor.tar.bz2.sha512 -o gvisor.tar.bz2.sha512
  sha512sum -c gvisor.tar.bz2.sha512
  mkdir -p gvisor && tar -xjf gvisor.tar.bz2 -C gvisor
  sudo install -m 0755 gvisor/runsc /usr/local/bin/runsc
  sudo install -m 0755 gvisor/containerd-shim-runsc-v1 /usr/local/bin/containerd-shim-runsc-v1
  sudo cp -r gvisor/gvisor-bin /usr/local/bin/
  ```
- **教训**：404 先别怀疑网络，**先验 URL 本身还存不存在**（`curl -s -o /dev/null -w "%{http_code}"` 一秒出结果）。"官方文档"也有新旧两条路，打不开就换另一条。

## 10. Docker Hub 直连 EOF：DNS 被污染，改走国内镜像

- **看到什么**：`docker pull busybox:latest` → `failed to do request: Head "https://registry-1.docker.io/v2/...": EOF`；`curl https://registry-1.docker.io/v2/` → `000`（连不上）。
- **为什么**：`getent hosts registry-1.docker.io` 返回 `2001:2::45` 和 `198.18.0.80`——**198.18.0.0/15 是基准测试保留段**，公网不可能出现，说明 DNS 被污染；`curl -v` 显示 IPv6/IPv4 都尝试后 TLS 握手被 EOF，是中间设备掐的。不是 docker 的问题，是这台机器到 Docker Hub 的路被动了手脚（同机 `storage.googleapis.com` / `download.docker.com` 都正常）。
- **怎么修**：逐个试镜像（`curl -4 -s -o /dev/null -w "%{http_code}" --max-time 10 https://<mirror>/v2/`，401/403 都算通，000 算不通）。实测这台机器上 USTC/163/腾讯云镜像全是 000，只有 `docker.m.daocloud.io` 通：
  ```bash
  docker pull docker.m.daocloud.io/library/busybox:latest
  ```
- **教训**：**拉镜像失败先分层**：`curl` 测连通性 → `getent hosts` 看 DNS → `-v` 看卡在哪一层。DNS 返回保留段 IP = 污染，别再重试了，直接换镜像。
